Abstract

Google's data center products and services documentation is written in DITA XML. DITA lets writers reuse content. A writer writes a warning or a spec value once and references it from many topics. The team now wants to move to docs as code: Markdown files in Git, reviewed in pull requests and built by CI (continuous integration).

Converting DITA to Markdown is easy. DITA Open Toolkit (DITA-OT), the free publishing engine the team already uses, does it with one command1. The hard part is what the conversion removes without a warning. It copies shared content into every topic, writes key values as plain text and drops element IDs. No team can read thousands of converted pages by hand, so these losses reach readers.

MANIFEST is a migration agent. It converts one DITA map at a time and proves that the converted topics are complete. Gemini runs the migration and fixes problems. Fixed Python checks decide whether each topic passes. Topics that pass go into a pull request for a writer to approve. Topics that fail go to a writer with the reason.

§1 Client Brief

Google publishes documentation for its data center products and services, including Cloud TPU (Tensor Processing Unit) accelerators. This MVP uses a small part of the Cloud TPU documentation as its sample: the pages for four TPU generations (v5e, v5p, v6e and TPU7x), rewritten as DITA topics.

These pages are a good test because they repeat a lot of content. Each generation has the same spec table with different values. The same values appear in tables and in text. Different readers need different parts of the page. In DITA, writers handle this with three features:

DITA featureWhat it doesExample in the TPU pages
Content reference (conref)Reuses an element, such as a note or a table row, from another topic.One note about slice shapes, used in every generation's topic.
KeyStores a value once in the map. Topics refer to the key, not the value.tpu7x-chips-per-pod = 9,2164
Conditional contentMarks content for an audience. A DITAVAL file includes or excludes it at build time.Capacity-planning notes shown only to operators.

§2 Problem Statement

DITA-OT can publish DITA as Markdown in three formats: standard Markdown, GitHub-Flavored Markdown and GitBook1. The current release is 4.42. The team does not need a new converter. It needs to know what the converter changed.

2.1 What conversion removes

Before DITA-OT writes any output, it processes the source. It replaces each key reference with its value, copies each conref target into place and removes content that the DITAVAL file excludes3. The output is correct for one audience, but the reuse is gone. Nothing in the Markdown shows which text was shared or which values came from keys.

The GitHub format loses more. DITA-OT turns definition lists into bulleted lists and leaves out attribute blocks that hold IDs and class names1.

Example from a live page
The TPU7x page gives HBM capacity as 192 GiB in its comparison table and as 192 GB in the next section. It gives HBM bandwidth as 7,380 GBps in the table and as about 7.37 TB/s in the text4. When one value is typed in two places, the copies can drift apart. A key stores the value once.

Problem statement
The Google data center documentation team can convert DITA to Markdown with tools it already has, but it cannot prove that the converted content is complete. The conversion removes reuse, element IDs and conditional content, and it does not report these losses. Checking every page by hand is too slow for thousands of topics. As a result, the team cannot migrate at scale with confidence.

§4 User Stories

Each story comes from the Goal and Success fields in §3. The acceptance criteria are what the checks in §5 test.

US-01 · Docs Platform Lead
As the Docs Platform Lead, I want one report for each map that lists the topics that passed and failed and why, so that I can approve a migration without reading every page.
Accepted when: every map has a report · every failure links to the topic and the check that failed · no topic is skipped.
US-02 · Senior Technical Writer
As a senior technical writer, I want every conref and key to arrive as an include or a substitution, so that I can still change a value in one place.
Accepted when: includes in the output equal conrefs in the source · substitutions equal key references · any difference fails the topic.
US-03 · Information Architect
As an information architect, I want elements that have no Markdown equivalent sent to a writer, so that no structure is lost without a decision.
Accepted when: each unmapped element creates a review item · zero elements are downgraded without review.
US-04 · Software Engineer
As a software engineer, I want a check on my pull request that tells me if I broke a link, an include or a key, so that I can fix docs without a writer.
Accepted when: the check runs on every pull request · each error gives the file, the line and the fix.
US-05 · Technical Support Engineer
As a support engineer, I want every old URL and anchor to open the right page or redirect to it, so that links in past cases keep working.
Accepted when: each element ID is kept as an anchor · a redirect file is created for each map · links that cannot be resolved are listed by name.
US-06 · Priya (reader)
As an ML engineer, I want a spec value to be the same wherever it appears, so that I can size a slice from any page.
Accepted when: every keyed value comes from one substitution · the output has no typed copies of a keyed value.
US-07 · Tomás (reader)
As a site reliability engineer, I want to see only operator content and keep my bookmarks, so that the docs stay useful after the move.
Accepted when: the text for each audience matches DITA-OT's output for the same DITAVAL file · old anchors still resolve.

§5 Proposed Design

MANIFEST does one thing. It migrates a DITA map to MyST Markdown and proves that every topic is complete. It is an agent built with Agent Development Kit (ADK), Google's open-source agent framework. ADK is licensed under Apache 2.0 and its agents can run on Cloud Run14. Gemini 3.8 Flash (gemini-3.8-flash) runs the agent15 and calls its tools through Gemini function calling16.

The agent has five tools. Each tool is plain Python and gives the same result every time. The agent decides which tool to run next and how to fix a failed topic. The checks decide whether a topic passes. The agent cannot change a check result.

System context: MANIFEST added
Compare with Figure 1. The DITA source and DITA-OT stay as they are. The manual copy is replaced by the agent, and every topic now has a report.
5.2 Agent tools

1 · Count what is in the source inventory_map

Reads the map and its topics with Python and lxml. Counts elements, conrefs, key references, conditional attributes, element IDs and links in each topic. This count is the "before" picture that every check uses.

Output: inventory.json for each topic

2 · Convert with DITA-OT convert_map

Runs DITA-OT 4.4 with the standard markdown format, not the GitHub format, which drops more1. Before the run, the tool puts a placeholder in place of each conref, key reference and conditional block in a working copy. DITA-OT cannot resolve a placeholder, so the reuse survives the build. The DITA source is never changed.

Output: Markdown with placeholders · to test first in the MVP: placeholders pass through DITA-OT unchanged

3 · Put the reuse back restore_reuse

Replaces each placeholder with its MyST Markdown equivalent. Shared content becomes an include file. A key becomes a substitution. Conditional content becomes an only block. Each element ID becomes a target. §5.4 lists every mapping.

Output: MyST Markdown · _includes/ · substitutions file · build tags

4 · Check the topic check_topic

Runs three checks. Counts: counts the output again and compares it with the inventory. Text: builds the source with DITA-OT HTML5 and the output with Sphinx for the same DITAVAL file, then compares the text. IDs: confirms that every source ID is an anchor. Returns pass, or a list of differences.

Output: pass or fail, with the element and line for each difference

5 · Check the links check_links

Runs lychee, an open-source link checker, over the Markdown and the built HTML. It checks internal links offline and writes the result as JSON11. It also checks that every old URL has a redirect.

Output: broken links · redirect file for the map
5.3 Agent loop

The agent runs tools 1 to 5 for each topic. When check_topic reports a difference, Gemini reads the difference and the source, and proposes a fix. For example, it maps an element that has no rule yet. The agent applies the fix and runs the check again. After two failed fixes, it stops and opens a review issue for a writer. The issue contains the source, the output and the check result.

When a writer approves a fix, MANIFEST saves it as a new mapping rule. The next map uses the rule without calling Gemini.

Figure 5
What happens to one topic
Gemini is called only for topics that fail a check. Topics that pass on the first run never use the model.
5.4 Reuse mapping

MyST Markdown supports substitutions, set in the project configuration or in a page's front matter8, and an include directive18. Sphinx's only directive includes content based on tags set at build time9. Together they cover the three DITA reuse features.

DITAMyST MarkdownHow the check proves itMVP
ConrefInclude file in _includes/, written onceIncludes in the output equal conrefs in the sourceMapped
Key referenceSubstitution, for example {{ tpu7x_chips_per_pod }}Substitutions equal key references; no typed copiesMapped
Conditional content and DITAVALonly block with build tags; one build for each DITAVAL fileText matches DITA-OT output for the same DITAVAL fileMapped
Element IDTarget, for example (slice-shapes)=Every source ID is an anchorMapped
Specialised elements, conref push, key scopesNo ruleSent to a writer as a review issueWriter

One limit to know: Sphinx still processes content inside an only block that a build excludes, which can cause surprises when headings or links sit inside one10. The text check in tool 4 is there to catch this.

§7 Success Metrics

The MVP runs on the TPU sample map. It succeeds if the numbers below are met on that map. The first metric matters most: a migration that reports every loss is safe to review, even when it has failures.

MetricHow it is measuredMVP target
Unreported lossesLosses a writer finds after merge that the report did not list0
Topics checkedTopics with a report ÷ topics in the map100%
Reuse keptIncludes and substitutions in the output ÷ conrefs and key references in the source100% of mapped features
IDs keptSource element IDs that are anchors in the output100%
Broken linkslychee result after migration, including old URLs0
Topics passed without a writerTopics that pass on the first run or after a Gemini fixSet from the first run; tracked for each map
Fixes approvedGemini fixes that a writer approves ÷ fixes proposedTracked; each approved fix becomes a rule
